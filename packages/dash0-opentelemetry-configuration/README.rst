Dash0 OpenTelemetry Declarative Configuration
=============================================

Declarative (file-based) SDK configuration for the Dash0 OpenTelemetry Python
distribution, read from ``OTEL_CONFIG_FILE``.

The package is experimental. The vendored ``schema.json`` is the 1.1.0 release
of https://github.com/open-telemetry/opentelemetry-configuration, and
``_SUPPORTED_SCHEMA_MINOR`` in ``file/_loader.py`` records the highest
``file_format`` minor the loader knows. A file declaring a higher minor loads
with a warning that some settings may be ignored. Whether a setting this schema
does not carry is in fact ignored depends on where it sits, since the document
is validated before the ``file_format`` is read. The document root accepts an
unknown key. A block the schema closes rejects one and fails the load. A block
the schema leaves open, which is every plugin position, accepts one and then
fails at component construction with ``Plugin '<name>' not found``.

Do not edit this package by hand
--------------------------------

Everything under ``src/`` and the whole of ``pyproject.toml`` are generated by
``scripts/vendor_configuration.py`` from a branch of
https://github.com/dash0hq/opentelemetry-python. The ``UPSTREAM`` file records
both the branch and the exact commit. A hand edit here is reverted by the next
run of that script, and the ``vendored-configuration`` job in CI fails while it
is still present.

Two files are exempt, because the script leaves them alone: this README, and
``src/opentelemetry/_configuration/version/__init__.py``, which holds the
released version and is advanced by ``scripts/bump_for_release.py``.

Where a change belongs
----------------------

Changes to how configuration files are parsed, validated or applied go on the
fork branch that ``UPSTREAM`` names, as commits on top of an upstream commit.
A branch is named ``dash0-v<upstream version>`` after the upstream tag its
commits sit on, so ``dash0-v1.45.2`` carries the Dash0 commits on top of
upstream ``v1.45.2``. The older ``dash0`` branch sits on upstream ``v1.44.0``
and is no longer the one this package tracks.

A commit added to the branch ``UPSTREAM`` already names reaches the package
with::

    python3 scripts/vendor_configuration.py --commit <new sha>

A rebase onto a new upstream tag produces a differently named branch, so it
needs ``--branch`` as well. Rebase the branch ``UPSTREAM`` names onto the new
tag, push it under the name that tag gives it, then run::

    python3 scripts/vendor_configuration.py --commit <new sha> --branch dash0-v<upstream version>

Without ``--branch`` the script keeps the branch name already in ``UPSTREAM``
and writes the new commit beside it, leaving the file naming a branch the
commit is not on. ``--branch`` on its own is refused, because it would record
the other half of the same wrong pair.

``scripts/vendor_configuration.py`` stops when the fork's ``opentelemetry-api``
or ``opentelemetry-sdk`` pin disagrees with the distribution's, which is what
catches a change committed to a branch sitting on the wrong upstream tag.

Changes to how the code is packaged for this distribution go in
``scripts/vendor_configuration.py``. It owns the rename from
``opentelemetry.configuration`` to ``opentelemetry._configuration``, the
re-export shims at the path the SDK imports, and the dependency pins, which it
copies from the distribution's own pins rather than repeating them.

Why the implementation sits at a private path
---------------------------------------------

The implementation is installed as ``opentelemetry._configuration``, a path
upstream does not own, and ``opentelemetry.configuration`` holds only star
re-export shims. ``opentelemetry/sdk/_configuration/__init__.py`` imports
``opentelemetry.configuration`` by name, so the shims are what make
``OTEL_CONFIG_FILE`` work, while the private path means installing this
alongside a future published ``opentelemetry-configuration`` cannot collide
file for file. The pyproto exporter packages in this workspace use the same
arrangement.

What the fork changes
---------------------

Upstream validates configuration files with ``jsonschema``, which brings
``attrs``, ``referencing``, ``jsonschema-specifications`` and ``rpds-py``. All
four would land in the tree the injector adds to an application's
``sys.path``, and ``rpds-py`` is a compiled extension, so that tree would stop
being pure Python. The fork compiles the schema to plain Python with
``fastjsonschema`` at development time instead, leaving a validator whose only
imports are ``decimal`` and a sibling module of its own. The fork's own suite
checks that validator against ``jsonschema`` document by document.
